# Watchlist planning notes

Status: implemented. See [the feature guide](features/watchlists.md) and
[release checks](workflows/WATCHLIST_RELEASE_CHECKS.md) for behavior, verification,
and deployment-only gates. The investigation and planning-only notes below are
historical context. All watchlist test fixtures use synthetic athlete data.

## Product decisions

- Add Watchlist after Archive on the public Tournaments page, not admin.
- Mobile-first editor selects multiple upcoming/in-progress tournaments and individual athletes. Scope athlete search to registrations for the selected tournaments: only include athletes whose athlete.name matches registration_link_competitors.athlete_name within those registrations. Do not search the entire athlete database.
- Within that eligible pool, athlete text search checks both athlete.name and athlete.personal_name. The registration eligibility match uses athlete.name, not personal_name.
- Team search uses the team name in the athlete's registration for a selected tournament, not their most recent match team. Return individual athletes to add; no automatic whole-team selection. Keep the tournament filter on the registration rows used for team matching, and deduplicate athletes registered in multiple divisions or selected tournaments.
- Save only the tournament and athlete selection. Canonicalize, sort, and deduplicate identifiers and derive a versioned deterministic UUID. Persist its mapping to the selection, never a frozen copy of athlete or match data. Identical selections reuse an ID; changed selections generate a different ID.
- Open the saved view in a new browser window/tab. Prominently instruct users to bookmark it, provide Copy link, and explain that otherwise they must rebuild the selection.
- Edit selection returns to the main editor with the saved tournaments/athletes preloaded. Saving changes creates another ID and leaves the original selection intact until expiration.
- Display exactly one row/card per athlete, using their earliest next match across all selected tournaments and divisions, including newly appearing open-class matches. Sort scheduled athletes by next-match time ascending.
- Treat order-of-fights dates and times as local to the user. Preserve, display, and sort the published calendar date and clock time directly; no timezone metadata or conversion is needed.
- Show time, mat, opponent, opponent rating and win chances, with tournament/division context. Both athlete names link to their profiles on the main site where a local profile exists.
- Reuse existing division-based default ratings, open-class adjustments, win probabilities, match counts, and red/yellow provisional indicators. An unknown athlete has zero matches and a provisional default rating, not an unavailable rating.
- Preserve unresolved opponent descriptions such as Winner of Fight until a specific opponent is assigned; do not invent an athlete identity for a placeholder.
- When a tournament is running and an athlete appears on no mat, move them to the gray section. This means no listed match, not verified elimination or completion. Another selected tournament's next match takes precedence over an absent entry.
- Show not-yet-published schedules explicitly. Order-of-fights requests can error before a tournament is live.
- Refresh data every three minutes while open, without resetting scroll. Refresh overdue data when returning to the page. Retain the last successful data on errors.
- On an initial load where none of the selected tournaments has ever produced a successful snapshot, show "Populating tournament data, please wait…" without schedule cards. Use the same three-minute polling interval during initialization and after failures. Show cached data as soon as any selected tournament has a successful snapshot.
- URLs expire and are deleted a couple of days after tournaments finish. Proposed precise rule: latest selected RegistrationLink.event_end_date plus two days, so an earlier-finishing tournament does not expire a still-useful list.

## Agreed shared fetching design

- Order of fights is the sole live match source for this feature. Bracket requests are unnecessary under the agreed absence rule.
- Separate persisted selections from shared tournament/day/page schedule snapshots. Multiple watchlists reuse the same fetched and parsed data.
- Web requests have a 30-second timeout. A scan of many mats across multiple tournaments may exceed it, so requests must not wait for upstream fetching. Return the latest cached snapshot immediately and trigger background work for stale tournaments; return a populating state when no snapshot exists.
- Use one refresh unit per tournament, shared across all watchlists. A request atomically acquires an expiring database lease for each eligible stale tournament; only the lease holder starts a background thread. Other requests return cached data or initialization status without starting duplicate work. A process-local lock alone is insufficient across web-server processes.
- Each thread discovers the tournament's relevant days and mat pages, fetches with bounded upstream concurrency and per-request timeouts, and parses the results. Bound total refresh-thread activity as well as page-fetch concurrency so requests for multiple tournaments cannot create unlimited work.
- Publish a complete tournament snapshot atomically. Readers continue using the previous successful snapshot until replacement is ready. Tournaments publish independently, so one slow tournament does not block another.
- Give every lease a unique ownership token. Publishing, renewing, or releasing a lease must verify current ownership; a stalled thread whose lease expired must not overwrite a newer refresh. Choose a lease duration/renewal policy that supports slow scans while allowing recovery after a worker dies.
- Apply failure backoff and retain successful data when fetching/parsing fails. Release owned leases on normal completion/failure; expiry allows a later request to retry after a crash or failed thread startup.
- Background threads need their own application context and database session, with cleanup when they finish. Verify that the deployment permits threads to continue after an HTTP response. Worker recycling may interrupt work; leases and atomic publication must make that recoverable.
- Keep the last successful snapshot. Do not turn fetch errors, parse failures, or missing pagination coverage into an empty schedule or an absence decision.
- Discover all relevant days and mat pages, including changed pagination and newly assigned/open-class fights. Establish complete coverage before classifying an athlete as absent. Avoid relying exclusively on previously observed mats.
- Use demand-triggered background threads in the existing app; no Celery or separate refresh service is planned. Measure scan latency and resource usage to size concurrency, leases, and backoff. Background scans may outlast an HTTP request without keeping that request open.
- Client polling does not imply one upstream refresh per client. Cache freshness, shared leases, and backoff govern upstream traffic.
- Enforce expiry at read/save time independently of physical cleanup. Use an existing scheduled maintenance path if available for deletion; investigate that path before specifying a new process.

## Investigation findings

- Existing background-thread entry points are save_competitors_thread and update_live_ratings_thread in app/routes/brackets.py. Both use app.app_context(). This establishes a code precedent, not proof of deployed worker behavior. requirements.txt pins gunicorn 23.0.0; no production launch command or scheduled-maintenance configuration was found in the inspected repository paths.
- A planning probe fetched all nine pages of tournament 3027/day 5067 with concurrency four: 34 distinct mats, all HTTP 200, 6.353 seconds total, individual requests 0.829–6.195 seconds. Pages were approximately 1.008 MB each despite eight pages having no fight cards. This is one network sample, not a production or worst-case benchmark. The populated day 5068/page 2 sample was approximately 1.25 MB and took 2.638 seconds. Do not store repeated search-widget payloads in snapshots.
- Day navigation includes single-quoted links, while other links use double quotes. Parse HTML with BeautifulSoup, not regex. The homepage linked 3027 to day 5067, while the day sidebar exposed 5066, 5067, and 5068. Therefore homepage discovery must be followed by sidebar discovery.
- Mat containers use .sliding-columns__column, .grid-column__header, and ul.tournament-day__mats. Fight entries contain .match-header__when, .match-header__fight, .match-header__category-name, and competitor-N IDs. Placeholder sides use .match-card__child-description / .match-card__child-where.
- The last page links to itself as well as its predecessor. Maintain a visited set; do not interpret every page link as another page to fetch.
- The day 5067 sample retained one blue fight card while the next day's sample had yellow cards. Color/status meaning has not been established. Do not infer completion from color or elapsed scheduled time. The agreed source-presence rule applies to listed cards, even if IBJJF retains a delayed or old-looking card.
- get_ratings currently queries by IBJJF ID OR normalized name. Reuse requires an explicit strict-ID option or a separated identity-resolution helper; calling it unchanged would violate Watchlist identity rules.
- compute_match_ratings in app/routes/brackets.py applies weight_handicaps and EloCompetitor.expected_score. app/frontend/src/utils.ts:immatureClass defines provisional as <=4 matches and semi-provisional as <=6. Reuse these rules and styles.
- RegistrationLinkCompetitor has athlete_name, team_name, division_id, and registration_link_id. Its existing composite index starts with athlete_name; Athlete has normalized-name indexes but no explicit raw-name index in the inspected model.
- Public routes must be added to both app/app.py and app/frontend/src/App.tsx. Brackets.tsx owns the tab union and tab shell. Existing registration-links API returns display names and links only, so Watchlist needs a structured tournament endpoint.

## Implementation layout and persistence

- Add app/watchlist_schedule.py for pure discovery/parsing/normalization, app/watchlist_refresh.py for leases and thread lifecycle, app/watchlists.py for selection/search/row assembly, and app/routes/watchlists.py for thin public endpoints. Register its blueprint in app/app.py. Keep HTML parsing independent of Flask and database state.
- Add models and an Alembic migration under app/migrations/versions. Use the project's UUID/JSON-compatible conventions so ordinary unit tests can still use SQLite; exercise concurrency against PostgreSQL separately.
- Watchlist: id (UUID primary key), schema_version, canonical_selection (JSON containing sorted distinct event IDs and local athlete UUIDs), created_at, expires_at; index expires_at. Store no athlete display/rating/schedule fields here. Event IDs are strings, matching RegistrationLink.event_id. Hash versioned canonical JSON with uuid.uuid5 and a fixed application namespace. Compare canonical payloads on conflict; identical submissions are idempotent, and an unexpected differing payload is an error.
- WatchlistSchedule: event_id primary key, snapshot JSON, snapshot_version UUID, fetched_at, coverage JSON, discovery metadata, refresh_token UUID, lease_until, next_attempt_at, failure_count, last_error_code. Empty successful snapshots are distinct from null/no snapshot. Store normalized matches and source metadata only, not megabytes of search-widget HTML. Coverage records day IDs, dates, page URLs and mats, plus unpublished days.
- WatchlistRefreshSlot: a small fixed set of slot IDs with owner token and lease_until, providing a global bound across processes. Claim a slot and the tournament lease in one short transaction; if either fails, roll back. Use conditional updates/row counts and deterministic locking order. Never hold a transaction or database connection while waiting for HTTP.
- Add indexes on registration_link_competitors(registration_link_id, athlete_name) and athletes(name) for the exact eligibility join. Verify query plans against realistic data before adding further text/team indexes; the filtered registration pool should keep substring filtering small.

## Search and selection contract

- GET /api/watchlists/tournaments: return event_id, registration link IDs, name, start/end dates, and registration availability. Restrict to public external IBJJF tournaments with an event ID and an end date that has not passed, using the site's existing registration-date conventions. Deduplicate multiple links for one event. Internal sources without IBJJF IDs cannot supply order-of-fights data.
- GET /api/watchlists/athletes?event_id=...&q=...&mode=name|team&cursor=...: require selected tournaments, return 30 distinct athletes per page with stable display-name/UUID ordering and their registration team/tournament context. Use an EXISTS or distinct eligible-ID subquery joining Athlete.name = RegistrationLinkCompetitor.athlete_name, scoped through RegistrationLink.event_id. Search normalized name and normalized_personal_name for name mode; team mode filters registration team_name on those same selected-event rows. Escape wildcard input and bind parameters.
- Preserve existing hide_full_name display behavior while allowing the explicitly requested name/personal_name search. Deduplicate by local athlete UUID, never by name. Two local athletes with the same name remain distinct choices. Athletes with a null ibjjf_id can be displayed disabled with an explanation that live tracking is not available; do not silently match them to fight cards by name.
- Registration search reads local registration data; it must not synchronously import every tournament on each keystroke. Show an explicit registration-data-not-ready state if no imported data is available, using the existing registration import path in background if needed. Empty successful imports need a readiness marker rather than being indistinguishable from never imported data.
- POST /api/watchlists accepts event_ids and athlete_ids, validates current registration eligibility and live IDs, computes the canonical UUID and expiry, and returns id, url, expires_at. Require at least one tournament and athlete; start with configurable caps of 10 tournaments and 200 athletes. These are resource bounds, not assumptions about typical usage.
- GET /api/watchlists/<uuid> returns selection plus current athlete/tournament summaries for editing. GET /api/watchlists/<uuid>/data serves rows, per-tournament state/freshness, refreshing flags, and poll_after_seconds; it may trigger refresh leases but never waits for upstream requests. HTTP 200 covers populating/partial/stale states; malformed input is 400, missing ID 404, and an expired existing record 410. After physical deletion, the same unavailable/expired UI handles 404.
- Saved selections follow athletes across every division in each selected tournament, regardless of the registrations used to find them. Do not persist division filters or revalidate registration eligibility on every saved-view read; registration changes must not erase an existing selection. Editing/saving validates the new selection and explains any no-longer-eligible athlete.

## Parsing, coverage, and row reduction

1. Fetch the shared homepage discovery cache (five-minute TTL, own cross-process lease) and locate the tournament's day link. Discover all days from that page's sidebar. Use locale=en consistently and restrict discovered fetch URLs to the expected IBJJF host/tournament and numeric day/page paths.
2. Parse full day dates using the event year/date range, including year rollover. Scan today and future published days for next matches. Past-day fights do not override a later next match. Rediscover days and pagination on each refresh so open-class additions and changed mat counts enter the next snapshot.
3. Fetch page 1 for each relevant day, use the advertised mat count to seed four-mat page groups, then reconcile actual pagination links, visited pages, and distinct mat headers. Exhaust discovered links; require advertised mat coverage where available. A missing/duplicate mat, changed page structure, or unresolved pagination edge makes that day incomplete. Retry topology discovery once if it changes during a scan, then retain the previous snapshot on continued inconsistency.
4. Normalize each card into event_id/day_id/local_date/mat/fight_number, published clock time, division context, and two sides (IBJJF ID/name/team or unresolved predecessor description). Keep date and time as local calendar/clock values throughout storage and API serialization; do not append a UTC suffix or let browser parsing shift the displayed time. Key a match by event/day/mat/fight number; keep source order as a deterministic fallback. Do not count athlete IDs in search widgets as appearances.
5. A valid day with all expected mat containers and no fights is a successful empty schedule. A known future day that is not published is recorded as unpublished and retried later. An arbitrary 500, timeout, login/error page, or unrecognized HTML is a failure, not evidence of absence or publication status. Missing discovery before event start can be shown as not posted; once running, uncertain failures are shown as temporarily unavailable.
6. Use source presence for eligibility, not now > scheduled time. Delayed fights remain visible. Ignore neither blue nor yellow cards based on unverified color semantics. Retained source cards may remain visible until IBJJF removes them; that is consistent with the agreed absence heuristic.
7. For each selected athlete, take the earliest listed match by published calendar date and clock time across selected tournaments, treating all times as local to the user; tie-break by event/day/mat/fight number. Unknown-time listed matches remain visible with Time pending after timed matches, before gray athletes. If both watched athletes face each other, retain both athlete rows as requested.
8. With no listed match, gray an athlete only when relevant running-tournament coverage is complete and reliable. Show Not on current schedule, not Finished. Future/unpublished coverage shows Schedule not posted; failed/partial coverage shows Unavailable or stale status. Never add an incompleteness warning to a cached known match.

## Ratings and response assembly

- Batch resolve selected competitors and opponents by exact IBJJF ID, then group rating inputs by event, gi/no-gi, date, age/belt/gender/weight. Add strict-ID resolution to get_ratings with existing callers retaining their current default behavior, or extract a shared helper with separate identity policies.
- Reuse get_ratings and compute_match_ratings through an adapter producing their required fields; preserve default ratings, last_weight/open-class handicaps, and live-rating reads. Watchlist must not synthesize match results or update live ratings from schedule cards, which do not establish outcomes.
- Unknown actual opponents receive a division default and match_count=0. An unresolved Winner of Fight slot is not an unknown athlete: retain its description and omit a fictitious prediction until an opponent exists. Preserve existing supported-age rating policy rather than inventing new youth ratings.
- Reuse immatureClass, existing dot styling, rounded probability display, and profile slug/UUID links. Keep rating enrichment local and batched; no per-athlete HTTP calls or photo scraping during a Watchlist request. Cache enriched responses briefly by snapshot versions and selection if measurements require it, without tying ratings to permanent selection storage.

## Initial refresh operating defaults

- Successful schedule TTL: 180 seconds. Two globally leased tournament slots, two page requests per tournament (maximum four upstream page requests across workers), and a process-local bounded executor as an additional resource bound. Treat discovery as part of the same upstream budget. No unbounded work queue: when capacity is full, return a short retry hint and let a later poll try again.
- Connect timeout 5 seconds, read timeout 20 seconds; total refresh deadline 10 minutes. Lease duration 90 seconds, renewed at most every 20 seconds while work progresses, for both slot and tournament. Use database UTC time and a monotonic clock for the in-process deadline. A lease may not be renewed beyond the total deadline.
- On failure, next-attempt delay 30 seconds doubling to at most five minutes, with jitter; honor upstream Retry-After when longer. Reset failure count after successful publication. No tight retry loop inside the refresh. Stop starting work immediately on lease loss; outstanding HTTP calls remain bounded by timeout.
- Publish only while the ownership token and lease are valid, updating snapshot, coverage, version and freshness in one transaction, then release the owned slot. Stage data in thread memory or token-scoped temporary rows; never mix old and new page generations in a published snapshot.
- Poll every 180 seconds in every state, including initial population and failures. Pause polling while hidden and recheck when visible. The server records timestamps per tournament; an API response timestamp must not masquerade as source freshness.
- Log event/token, queue/claim outcome, pages/bytes, fetch/parse duration, coverage outcome, and stale age. Never log full upstream HTML. Use these observations to tune defaults after a busy-weekend trial.

## Expiration and cleanup

- Define expiry as the latest selected RegistrationLink.event_end_date plus two days, using the site's existing database date conventions. Store expires_at and show the resulting date in the editor/view.
- Require a known end date before offering a tournament for new selection; surface missing end dates explicitly rather than creating immortal URLs or guessing a date. Reconcile expires_at if authoritative event dates change, without changing the canonical selection/UUID.
- Reads enforce expiry before triggering work. Add a purge-expired-watchlists Flask CLI command following the existing app.cli.command pattern. Deploy it through the hosting scheduler daily; no scheduler configuration was found locally, so the actual job registration is a deployment task. Also delete an expired record encountered on access. Remove orphaned schedule caches after all watchlists have expired and retain no live lease during cleanup.

## Frontend implementation

- Add Watchlist to the Tabs union and render WatchlistEditor.tsx at /tournaments/watchlists. Add WatchlistView.tsx at /watchlists/:id, and /tournaments/watchlists?edit=<uuid> for preloading. Register direct Flask routes using render_index_with_fallback, without generating SEO snippets.

Open profile links on the main site in a separate tab so the watchlist stays available. Stable athlete keys preserve focus and scroll across refreshes; gray cards remain readable. ## Explicit verification limits

- Production worker arguments, thread lifetime under hosting, and scheduler access cannot be verified from the inspected repository alone. Validate them during the release checks; the plan does not claim they were tested.
- The observed pages do not establish a reliable completed-fight color code. The implementation deliberately follows listed presence, preserving delayed cards, rather than introducing bracket fetching or guessing color semantics.
- Network measurements above are a small current sample. Worst-case capacity and query-plan checks remain implementation validation tasks, not reasons to put scans back inside 30-second requests.

For implementation, run make test from the repository root in the repository's Python environment. No OCR tests are needed and no routine frontend build should be run. Add a feature guide and index it once the feature is implemented.
